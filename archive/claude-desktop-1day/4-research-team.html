TIER 4 · 검증된 장기 리서치

폰으로 시작해 두고 — 여덟 명이 일하게

📁 이번 단계 폴더 → 실습자료/04-리서치/

내 관심 주제를 폰에서 한 마디 던져 두면 — 책상의 Cowork이 8명 팀을 가동해 자료를 모으고, 사실을 확인하고, 출처를 검증한 보고서까지 만들어 줍니다. 회의 다녀오면 결과가 와 있는 워크플로.

📱폰에서 시작
8명이 분업으로
1검증된 보고서 + 도입안
▶ 작업 폴더 전환 — 새 프로젝트 X 
이제 04-리서치 폴더에서 작업할 거야.
프로젝트는 그대로 두고, 작업 컨텍스트만 옮기는 거야.

💡 주제가 막막하면 — AI에게 "이 주제에서 진짜 답해야 할 핵심 질문 셋"부터 묻게 시키세요. 그래야 8명이 흩어지지 않고 같은 방향으로.

WHY · 왜 폰으로, 왜 여러 명을

자리를 떠나도 — 팀이 일한다

한 명에게 한 번 시키는 건 한계

혼자 조사하면 빠르지만 — 자기가 쓴 걸 자기가 믿어버립니다. 출처도, 숫자도, 결론도. 한 사람으로는 검증이 안 됩니다.

팀으로 나누면 — 시간이 필요

8명이 단계별로 조사하고 검증하면 깊이가 다릅니다. 다만 5분 안에 끝나는 작업이 아닙니다. 그래서 — 폰으로 시작해 두고 다른 일을 합니다. 결과가 폰으로 옵니다.

"왔더니 책상에 검증된 보고서가 와 있더라" — 이게 오늘 만들 경험입니다.

RISK · 그냥 믿으면 안 되는 이유

링크

틀린 통계

EXAMPLE · "쿠팡 2024년 실적"

같은 질문 — 두 답

챗봇 ❌

"약 30조"

"약" 30조? 정확히 얼마? · 출처 링크 없음 · "추정" 표현 · 결국 내가 다시 검증.

팀 ✅

"31.8조 (DART)"

모든 숫자에 1차 출처 · 클릭 가능한 링크 · 교차검증 완료 · 보고서 그대로 사용 가능.

차이는 시간이 아니라 신뢰. 그대로 회의에 들고 갈 수 있는 보고서 vs 다시 검증해야 하는 답. (DART = 금융감독원 전자공시시스템 — 기업 실적의 1차 출처. 수치는 이해를 돕는 가상 예시.)

FLOW · 6단계 워크플로

한 마디 → 다섯 단계 → 검증 보고서

1

병렬 수집 — 리서처 3명이 분야별 동시 조사.

2

숫자 검증 — 팩트체커 A가 모든 수치 재확인 (반려 시 리서처로).

3

출처 검증 — 팩트체커 B가 링크·인용 맥락 검사.

4

작성 — 구성작가가 기승전결로 정리.

5

최종 관문 — 게이트키퍼가 팩트·맞춤법 재점검.

6

최종 보고 — 오케스트레이터가 형식(MD/Word/PDF) 선택해 전달.

워크플로 = 일이 단계를 따라 흘러가는 순서. 어디서 막혀도 — 그 단계 담당이 다시 받아 보냅니다. 자동 반려 + 자동 재작업.

PRINCIPLE · 원소스 우선

출처에도 — 순위가 있다

1

기업·기관 원본 — 공시(DART), 공식 발표, 실적 자료 → 팩트체크 생략 가능.

2

전문 분석 — 증권사·신용평가사 보고서 → 간소화.

3

공공기관 — 통계청·OECD·UN 등 공식 통계 → 간소화.

4

언론 보도 — 공인 매체의 1차 보도 → 교차검증 필요.

❌ 절대 금지 — 위키피디아·블로그·커뮤니티. 1순위에서 답이 나오면 거기서 멈춥니다.

준비물

  • 데스크톱과 같은 계정으로 폰 로그인

STEP 2 · 팀 인식시키기

7개 파일을 — 읽게 한다

팀템플릿 폴더의 정체

워크스페이스 04-리서치/팀템플릿/ 안에 SKILL.md + 6명 역할 .md가 미리 들어 있습니다. Cowork에게 이 파일들을 읽어 6단계 워크플로를 따라가게 시키면 됩니다.

팀 파일 읽히기 + 기억시키기 
04-리서치/팀템플릿 안의 SKILL.md랑 6개 역할 파일을 다 읽어 둬.

각 역할이 무슨 일을 하는지,
워크플로가 어떻게 흐르는지 한 줄씩 요약해서 알려 줘.

앞으로 내가 "리서치 팀 돌려 줘"라고 하면,
팀템플릿의 6단계 워크플로를 순서대로 따라가서 검증된 보고서를 만들어 줘.
기억해 둬.

한 번 읽혀 두면 — 다음부터는 주제만 주면 6단계 워크플로가 따라옵니다.

STEP 3 · 폰에서 내 주제로 — 장기 작업 시작

한 마디 던지고 — 자리를 비운다

⭐ 오늘의 핵심 실습

본인이 평소에 깊이 알고 싶었던 주제 하나로 — 팀이 진짜 리서치를 돌리게 합니다. 폰에서 시작해 두고, 책상으로 돌아왔을 때 보고서가 와 있게.

▶ 내 주제 — 장기 리서치 시작 
내 관심 주제는 **[여기에 주제]**야.

이 주제로 04-리서치/팀템플릿 워크플로대로 검증된 보고서를 만들어 줘. 진행은 이렇게.
1) 시작 전에 — 주제를 더 구체화하기 위해 필요한 질문 5개 이내로 먼저 물어봐.
   내가 답하면 그걸 바탕으로 핵심 질문 셋을 정리해서 보여 줘.
2) 핵심 질문이 확정되면 8명 팀 가동.
   리서처 3명 병렬 수집 → 팩트체커 A·B 검증 → 구성작가 집필 → 게이트키퍼 관문.
   각 단계 끝날 때마다 폰으로 짧게 알려 줘.
3) 사용자 결정이 필요한 시점(예: 자료 부족, 방향 갈림)엔 멈추고 폰으로 물어봐.
4) 결과물은 04-리서치 폴더에 "보고서.md"로 저장. 출처 링크, 숫자 근거, "확인 필요" 항목 모두 포함.

⚠️ 폰에서 짧게만 시키면 결과도 짧음. 그래서 — 시작 프롬프트는 길어도 OK. 한 번 길게 시키고 진행은 폰에서 짧은 답으로.

STEP 4 · 결과 활용 — 도입과 추후 과제

보고서로 끝내지 않고 — 행동까지

▶ 보고서 → 한 장 요약 + 도입안 + 추후 과제 
방금 완성한 04-리서치/보고서.md를 바탕으로 세 가지를 더 만들어 줘.

1) 한 장 요약 — 04-리서치/한장요약.md
   상사에게 1분 안에 보고할 수 있는 분량.
   핵심 결론, 근거 3개, 숫자 3개, 권고 1줄.

2) 도입 방안 — 04-리서치/도입방안.md
   이 보고서 내용을 우리 팀이 실제로 적용하려면?
   3가지 구체 방안을 — 각각 "처음 한 주에 할 것 / 한 달 안에 할 것 / 분기 단위로 할 것"으로.

3) 추후 연구 과제 — 04-리서치/추후과제.md
   이번 보고서로 답하지 못한 질문 3개.
   각 질문마다 — 답하려면 무엇이 더 필요한지 한 줄로.

세 파일 다 만든 다음, 폰으로 "끝났어. 파일 위치는 ..." 한 줄로 알려 줘.
⚠️ 조심 "도입 방안"은 AI가 일반론으로 채우기 쉬움. 우리 팀 맥락이 안 들어가면 종이 위 계획. 도입안 카드 받은 뒤 — "우리 팀은 X 상황인데, 어떻게 조정?" 한 번 더 물어볼 것.
💡 가져갈 것 보고서 → 한 장 요약 → 도입안 → 추후 과제. 이 네 가지가 한 번에 나오는 게 진짜 가치. "보고서를 만든다"가 아니라 "다음 행동을 정한다"가 리서치의 목적.
ROLES · 팀원들 자세히 보기

팀템플릿 폴더 열어서 — 한 명씩 만나보기

왜 직접 봐야 하나

방금 Cowork에게 읽혔지만 — 실제로 어떻게 적혀 있는지는 내가 한 번 봐야 합니다. 역할 .md 파일 하나하나가 8명을 어떻게 일하게 하는지의 설계도. 나중에 내 팀을 직접 만들 때 참고할 모범 사례이기도 합니다.

어떻게 열어 보나

파일 탐색기에서 실습자료/04-리서치/팀템플릿/ 폴더를 직접 열어 보세요. 안에 SKILL.md(전체 흐름) + 6개 역할 파일이 있습니다. 메모장이나 VS Code, 또는 Cowork에게 "오케스트레이터.md 열어서 보여 줘" 식으로.

💡 다음 두 슬라이드에 핵심만 정리해 두었습니다. 더 자세한 건 .md 원문에서.

ROLES · 팀원들의 한 줄 헌법 (1/2)

조사·검증의 — 앞단

리드

오케스트레이터

"쪼개고, 돌리고, 마지막에 본다." 사용자 주제를 세 갈래로 쪼개 리서처에게 나눠 주고, 6단계를 끌고, 끝에 한 번 더 봅니다. 1차 출처에서 답이 나오면 더 넓히지 않고 멈춥니다.

조사 ×3

리서처 1·2·3

"재료를 모으는 사람." 분야를 나눠 동시에 1차 자료만 수집. 결과는 결론이 아니라 링크가 달린 재료 목록. 위키피디아·블로그·커뮤니티는 실마리로도 안 씁니다.

검증 A

팩트체커 A — 숫자 전담

"숫자만 봅니다." 매출·점유율·통계·단위·기준 시점만. 출처 판정은 B의 몫이라 손대지 않습니다. 원 출처와 직접 대조해서 같은 숫자인지 확인.

반려 규칙

즉시 되돌리기

원 출처에서 못 찾는 수치 / 원문과 다른 숫자 / 단위·시점 누락 — 이 셋 중 하나라도 보이면 사유를 적어 리서처에게 다시 보냅니다.

ROLES · 팀원들의 한 줄 헌법 (2/2)

집필·관문의 — 뒷단

검증 B

팩트체커 B — 출처 전담

"출처만 봅니다." 링크가 실제로 열리는지, 기관이 실재하는지, 인용이 원문 맥락과 같은 뜻인지. 수치는 A가 봤으니 다시 안 봅니다. 링크는 직접 열어서 확인.

작성

구성작가

"검증된 재료로만 씁니다." 짜임은 — 요약 3줄 → 본문 → 시사점 → 활용 한 걸음 → 참고 자료 표 → 확인 필요. 못 채운 빈칸은 지어내지 않고 "확인 필요"로 정직하게.

관문

게이트키퍼

"문 앞의 마지막 사람." 1관문은 팩트 표본 재검사(가장 중요한 숫자 2~3개만), 2관문은 문장 품질(맞춤법·호응·군더더기). 둘 다 통과해야 사용자에게 갑니다.

공통 헌법

네 가지 약속

① 1차 출처 우선 ② 위키·블로그·커뮤니티 금지 ③ 모르면 "확인 필요"로 정직하게 ④ 1차 출처에서 답이 나오면 더 안 넓힘.

💡 이 6개 역할 + SKILL.md의 공통 헌법이 곧 8명의 일하는 방식. 본인 팀을 만들 때 이 구조를 그대로 가져다 응용할 수 있습니다.

CHALLENGE · 더 나아가기

전문가처럼 — 도전 과제

도전 과제
  • ① 신뢰 출처 한정 — 공식 기관·통계청·국제기구·논문 사이트만 허용. 그 외 출처가 발견되면 자동 제외 + 사유 메모.
  • ② 보고서 → 발표자료 — 완성된 보고서를 5장짜리 PPT로. 출처·숫자 근거는 부록 슬라이드로.
  • ③ 9번째 일꾼 추가 — "결론을 일부러 반박하는 레드팀" 역할 파일(레드팀.md)을 직접 만들어 팀템플릿에 추가, 게이트키퍼 앞 단계로 끼워 1회전 돌리기.
  • ④ 정기 갱신 — 매주 월요일에 같은 주제를 재리서치하고, 지난주 대비 변화점만 별도 diff 보고서로.
