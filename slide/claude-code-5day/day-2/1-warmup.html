WHAT · API가 뭔가

API — 인터넷의 데이터 창구

한 줄로

다른 서비스가 가진 데이터를, 정해진 주소로 요청하면 데이터로 돌려주는 창구.

  • 날씨·책·포켓몬… 직접 모을 필요 없음
  • 요청하면 데이터 묶음(JSON)이 돌아옴
  • 그 데이터를 받아 화면에 보기 좋게 가공

자판기에 비유하면

자판기 버튼(주소)을 누르면 음료(데이터)가 나오듯 —

  • API 주소를 부르면 → 데이터가 나옴
  • 내부 구조를 몰라도 — 버튼만 누르면 됨
  • "이 API로 데이터 가져와줘" 한 줄이면 Claude가 코드를 씀

오늘은 공개 API(무료·가입 불필요)를 골라, 그 데이터를 가져와 가공해 화면에 보여주는 페이지를 만듭니다.

WHY · Plan을 켜는 이유

"5개 파일 동시 수정"이 계획서 없이 진행되면 위험.

큰 변경은 한 번 시작되면 멈추기 어려움. 미리 의도가 맞는지 사람이 한 번 봐야 사고가 안 남.

미리무엇을 어떤 순서로 할지 보임
선택승인 · 수정 요청 · 거절 — 사람의 판단 개입
결과의도와 다른 수정이 시작되기 전에 멈춤

ENTRY · 진입은 단축키로

Shift+Tab 두 번이면 됩니다.

1일차에 본 모드 순환 단축키. Interactive → Auto → Plan 순서이므로, 기본 상태에서 두 번 누르면 Plan.

한 번Interactive → Auto (accept-edits)
두 번Auto → Plan
세 번Plan → Interactive (복귀)
DECISION · 계획서 앞에서 3선택

읽고 나서 3개 중 하나

Approve

계획대로 실행

의도와 맞으면 그대로 진행. Claude가 단계별로 작업 시작 — 중간 권한 prompt는 여전히 동작.

Edit

수정 요청

"3번 단계는 빼고" "auth는 다른 폴더에" — 메시지로 의도 전달 → 새 계획서.

Reject

거절

방향이 완전히 틀렸을 때. 거절 후 더 작은 단위로 다시 시키거나 다른 접근.

처음 며칠은 Edit를 자주 쓰게 됩니다 — 의도 정밀도가 올라가는 과정.

WHEN · Plan을 켜야 하는 순간

매번 X — 큰 변경 앞에서만

✓ Plan ON

의도 어긋나면 손해 큰 일

  • 여러 파일 동시 수정 (5개 이상)
  • 의존성 추가 · package.json 변경
  • 리팩터링 · 구조 변경
  • 잘 모르는 라이브러리 도입
  • 처음 해보는 작업
/ Plan OFF (interactive)

작은 단위 · 자주 하는 일

  • 한 파일 안에서 함수 1개 추가
  • 오타 수정 · 스타일 미세 조정
  • 여러 번 해본 동일 패턴
  • Q&A 성격의 질문

감이 안 오면 Plan ON이 정답. 잘못 켰을 때의 손해는 거의 없음 — 시간 1~2분만 더 들 뿐.

실습 · Plan으로 만들기

계획을 확인·수정·논의하며 만들기

진행

  1. Shift+Tab 두 번 → Plan 모드
  2. 고른 공개 API로 "반응형 페이지 만들어줘"
  3. 계획서를 읽고 — 마음에 안 들면 Edit으로 구체적 수정 요청
  4. 계획이 좋으면 Approve → 제작 시작

프롬프트가 막히면 — 메타프롬프트

"어떻게 시켜야 할지 모르겠다" 싶으면, 프롬프트를 직접 짜기 전에 Claude에게 먼저 물어보세요.

  • "이런 페이지 만들려면 어떻게 시키는 게 좋아?"
  • "좋은 프롬프트로 다시 정리해줘"

Claude가 처음 낸 계획이 정답은 아닙니다 — 계획서를 같이 읽고 다듬는 게 핵심. 논의하며 만들어보세요.
